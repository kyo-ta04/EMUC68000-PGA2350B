# MS-BASIC 68K 再設計 R0-1 設計詳細化（2026-11-22）

状態：R0 の作業文書。確定しているのは原案 §6 の方針のみ。本書の案は Kyo の go/no-go 判断材料であり、決定ではない。
前提：メモリモデル A1（全面 32 ビット化）、整数 32 ビット、成功条件は「ASM.BAS が快適に動くこと」、R2 が山場、R3／R4 はオプション。

## 1. A1 メモリレイアウト案

前提の置き方：ボードは 256KB を (address & $3FFFF) でエミュレートし、ACIA はフルアドレスデコード。再設計版は **$0 配置を本線**とする（ファーム Route B と同じ土俵）。現行版の $30000 ローダ経路は EhBASIC 常駐が前提の配置であり、再設計版の配布はファーム統合が前提になる — これは割り切りとして明記しておく。

| 領域 | 用途 |
|---|---|
| $000000–$007FFF | インタプリタ本体（32KB 予算。現行 ext 16.5KB ＋ 整数演算・表機構の増分を見込む） |
| $008000–$00BFFF | ワークスペース：ZP-32、入力バッファ、制御スタック（FOR/GOSUB フレーム） |
| $00C000–$00FFFF | テーブル領域 16KB：変数ハッシュ 1KB、リテラルキャッシュ 6KB、行表（残り） |
| $010000–$03F7FF | プログラムテキスト → 変数 → 配列 → 文字列プール（約 190KB） |
| $03F800–$03FFFF | CPU スタック予約 2KB（初期 SP = $040000、文字列は MEMSIZ $03F800 から下方成長） |

- ZP-32 は現行の仮想 ZP のスロット配置と順序をそのまま維持し、ポインタ値を実 32 ビットアドレスに読み替える（移植差分を最小化する狙い）。TXTTAB／VARTAB／ARYTAB／STREND／FRETOP／MEMSIZ はすべて実アドレスになる
- FOR フレーム（現行 44B）は内包ポインタの 32 ビット化で再設計が要る（~52B 見込み、正確なレイアウトは R1 詳細設計の残件）
- 文字列記述子は 6B パック（長さ 2B ＋ アドレス 4B）を維持。奇数アドレス安全のためのバイト組み立てアクセス規律も現行から継承する
- ASM.BAS の所要：テキスト 42KB ＋ 行表 ~11.6KB ＋ 実行時変数・文字列でも、190KB に対して余裕が大きい。「入らない」問題は A1 で構造的に消える

## 2. R1 テーブル設計

方針：**表は高速化キャッシュであり、溢れても壊れても従来動作にフォールバックする**。表の有無でプログラムの意味が変わってはならない。

### 2.1 行表

- 形式：(行番号 2B, アドレス 4B, 予備 2B) = 8B／行、テキスト順＝行番号昇順
- 構築は RUN 冒頭の 1 パス。GOTO／GOSUB／THEN／RESTORE の行参照は二分探索、逐次実行は従来通りリンク辿り
- 16KB のテーブル領域に収まらない行数（約 1,100 行超）では行表を作らず従来の線形検索に落ちる。ASM.BAS は 1,454 行あるため、この上限設定は要再検討 — 行表だけ別枠（プログラム領域の先頭に動的確保）にする案を R1 詳細設計で詰める

### 2.2 変数検索のハッシュ化

- MS-BASIC の変数同一性は「先頭 2 文字 ＋ 型」だけである — ここが効く。名前キーからの 256 エントリ・ハッシュ表（値＝変数レコードへのポインタ、衝突はレコード側チェーン）で、PTRGET の線形 walk（M9 で 13.9%）をほぼ O(1) にする
- 変数レコード自体の形式（名前＋型＋値）は現行を維持。新規変数は実行時の初回参照で生成されるため、ハッシュへの挿入も実行時随時（DIM も同じ経路）。「RUN 時に一括解決」ではないので、プログラム編集に伴う無効化問題がそもそも発生しないのが利点

### 2.3 リテラルキャッシュ

- FIN の再解析税（FDIV10 込みで ~13%）への対策。キー＝テキストアドレスの直接マップキャッシュ：512 エントリ × 12B = 6KB（アドレス 4B ＋ FP 値 5B ＋ テキスト長 1B ＋ 有効フラグ）
- 実行中のプログラムテキストは不変なのでアドレスキーは安定する。ヒット時は値のコピーとテキストポインタ前進だけで済む
- 無効化：プログラム編集（行入力・NEW・LOAD）で全消去。STOP／CONT では保持する（編集が入れば編集側で消える）。DATA の数値リテラルも READ 経由で同じキャッシュに乗る

## 3. R2 型意味論 — 決定リスト（推奨付き）

R2 が山場である理由の中心はここにある。コード量ではなく、後から変えにくい意味論の判断が並ぶ。いずれも「MBASIC そのまま」の原則に照らし、BASIC-80 の言語仕様を参照元とする（コード輸入はしない）。

| # | 論点 | 推奨 | 代替案・リスク |
|---|---|---|---|
| D1 | リテラルの型 | 小数点・指数のない整数リテラルは int32 に収まれば整数型（&H も同様） | 全リテラル FP（現行）では整数演算の入口が細り、R2 の意味が薄れる |
| D2 | 演算子の型規則 | ＋−＊ は両辺整数なら整数演算。／ は常に FP（BASIC-80 踏襲）。￥（整数除算）と MOD を BASIC-80 から言語仕様として採用。比較は混合時に整数を FP 化して値で比較 | ／まで整数化すると原典の振る舞いから大きく外れる |
| D3 | オーバーフロー | int32 演算の溢れは黙って FP へ昇格（BASIC-80 の型昇格に倣う） | ?OV エラー（GW 系）。ASM.BAS のアドレス計算では昇格の方が実用 |
| D4 | FOR 変数 | 整数 FOR 変数を許可する（現行は原典通り ?SN で拒否 — ここは意図的に原典から外れる）。STEP・上限も整数で閉じる | 原典踏襲では ASM.BAS のループが全部 FP のまま |
| D5 | 代入変換 | FP → ％ 代入は現行の ROUND→AYINT→QINT 鎖を維持（互換優先）。整数 → FP は 2^32 まで厳密 | 変換規則を変えると既存プログラムの振る舞いが静かに変わる |
| D6 | 組み込み関数 | PEEK／DEEK／LEEK は整数を返す（アドレス値、ASM.BAS の主用途）。SGN は整数、ABS は引数の型を保持、INT は整数に恒等・FP に従来動作。SQR／SIN 等は常に FP | — |
| D7 | 配列 | 要素型ごとに演算する（％ 配列の要素は整数として load／store）。現行「保存専用」だった部分の実演算化 | — |
| D8 | USR | 引数・戻り値の型を型タグで受け渡す（現行 ext の A0＝FAC アドレス規約に型の解釈を追加） | 規約を壊すと現行 ext の USR 資産と非互換になる |
| D9 | PRINT | 整数は整数として印字（小数点なし）。末尾スペースは現行 NUMSPC 規約を踏襲 | — |
| D10 | READ／DATA | DATA の数値リテラルは D1 と同じ規則で型付け。％ 変数への READ は D5 の変換を通す | — |

## 4. FAC レジスタ割当（スケッチ）

- FAC：D4 ＝ 仮数 32 ビット、D5 下位バイト ＝ 指数。符号は仮数最上位ビット（MS 形式の符号・大きさ表現をそのままレジスタに載せる）
- ARG：D6 ＝ 仮数、D7 下位バイト ＝ 指数
- スクラッチ：D0–D2、A0–A2。A6 ＝ TXTPTR（現行規約を維持）。A5 ＝ 直近の変数レコードポインタ（PTRGET の戻り値を保持する経路用）
- 呼び出し契約：数値パック関数は FAC を D4／D5 で受け取り D4／D5 で返す。メモリ上の FAC は互換シャドウとして ZP に残し、文境界などメモリ前提の箇所でのみ同期する
- 効果見込み：FAC 交通 5.9% の消滅に加え、数値パック内部のメモリアクセス削減。実数は R0-2 の乗算プロトタイプで測る

## 5. 文字列モデル

- 推奨：現行の記述子 ＋ GC 方式を維持する。M9 では文字列・GC は 0.03% だが、ASCIIART は文字列が軽いプログラムなので過小評価の可能性がある
- Kyo の「必要であれば変更可」は温存する。ASM.BAS 形状（行文字列の連続処理）で GC コストが問題として実測されたら、その時に切る札
- ただし R2 の型伝播には文字列型も含める（連結・比較の分岐を型で決めるため）

## 6. R0-1 の残件（R1 詳細設計へ）

- FOR フレームの 32 ビット化後の正確なサイズとレイアウト
- 行表の置き場所（テーブル領域 16KB では ASM.BAS の 1,454 行が溢れる。プログラム領域先頭への動的確保案の詳細）
- 数値パック原生化の対象優先順位（M9：NORMALIZE 9.6%、FMULT のビット逐次乗算、FDIV の復元除算。R0-2 の計測と合わせて決める）
