# 文字列 GC 最適化 設計検討 — MS-BASIC 68K R2（2026-11-23）

問い：R3 の前に、文字列コレクタ（原典方式の全走査型 GARBAG）を最適化する
価値と方法を、実測に基づいて決める。本書は設計検討であり、実装の判断は
Kyo が行う。

前提実測（redesign-r25-profile-2026-11-23.md）：ボス PASS 1 第2周では
GC 一族が 88.31%（GC_CHK 43.09%＋GB_AE 32.71%＋GC_RTS 5.64%＋GB_V1
4.52%＋GB_VBUMP 1.84%）。フルラン実測 951,543,900,000 サイクル。

---

## 1. 現行アルゴリズムの地図

対象コード：redesign/parts/64-core-b3.asm の GETSPA／GARBAG／GC_CHK
（呼出側に 60-core-b.asm の DIM 経路）。ディスクリプタは DSCLEN=6 バイト
（データポインタ long ＠+0、長さバイト ＠+4、パッド ＠+5）。

### 1.1 誰が GC を起動するか（呼出点は3つだけ）

| 起動者 | 条件 | 失敗時 |
|---|---|---|
| GETSPA（文字列割当の唯一の入口） | FRETOP−要求長 ＜ STREND の不足時のみ。GCSW フラグで1回の呼出につき収集は1回まで | 再試行でも不足なら ?OM ERROR |
| FRE(x) 関数（FREFN） | **無条件**に1回収集し、FRETOP−STREND を返す | — |
| DIM（配列確保、60-core-b） | STREND＋ブロック長 ＞ FRETOP のとき1回収集 | 再判定でも不足なら ?OM ERROR |

GETSPA の呼出元は STRINI（連結・部分文字列・文字列関数の結果すべて）、
PUTSTR のコピー経路、CHR$／GET の1バイト構築など、文字列を生む全経路。

### 1.2 1回の収集（GARBAG）の手順

1. FRETOP := MEMSIZ、FRESPC := MEMSIZ（文字列空間の天井から再充填）。
2. **探索パス**：ディスクリプタ所有者を固定順に全走査する。
   - 走査1：テンポラリ・ディスクリプタ（TMPDSC..TEMPPT、最大3件）
   - 走査2：単純変数（VARTAB..ARYTAB、8バイト記録。名前2バイトの
     ハイビットで型判定し、文字列のものだけ）
   - 走査3：配列（ARYTAB..STREND のブロック列。文字列配列の要素だけ、
     要素は DSCLEN 刻み）
   各ディスクリプタは GC_CHK で判定：長さ＞0 かつ データポインタが
   GCLOW 以上（GCLOW は STREND から始まる走査中の最大値）かつ FRETOP
   未満なら候補。最大ポインタの所有者が勝者（同点は**走査順で後勝ち**、
   GC_CHK の >= 規則）。
3. **移動**：勝者のブロック [ptr, ptr+len) を BLTU（バイト単位の後方
   コピー、約36サイクル/バイト）で上に詰め、終端が FRETOP に接する
   ように移す。勝者のディスクリプタのポインタを**その場で**新アドレス
   に書き換え、FRETOP := FRETOP − len。
4. 候補が尽きる（全走査で勝者なし）まで 2–3 を繰り返す。

### 1.3 複雑さとレイアウト契約

- 生存文字列 S 件・所有者 D 件に対し、収集1回は **(S+1) 回の全走査 ×
  D 件判定 ＋ S 回のブロック移動** ＝ **O(S·D ＋ 生存バイト数)**。
- 最終レイアウト（バイト同一性の契約）：生存文字列はすべて MEMSIZ に
  隙間なく詰められ、**収集前のアドレス降順**に並ぶ（元・最上位のものが
  最上位）。FRETOP ＝ MEMSIZ − Σ生存長。移動しなかったディスクリプタ
  （長さ0、プログラム内リテラル等の空間外ポインタ）は不変。
- もう一つの契約：**ディスクリプタはその場更新**。インタプリタの他部は
  「ディスクリプタのアドレス」を割当をまたいで保持し（FAC+4、CAT の
  スタック退避、PUTSTR の再読込）、データポインタ値は割当後に読み直す。
  新コレクタもこの2契約を満たせば、観測可能な差は生じない。
- 同点（同一データブロックを2つのディスクリプタが指す）場合、原典は
  後勝ちの1件だけを更新し、残りは古いポインタのままになる（実質的に
  データ破壊パス）。これを構造的に防いでいるのが PUTSTR のコピー規則
  （「GARBAG は1ブロックにつき1ディスクリプタしか更新しないので、
  2変数が1ブロックを共有してはならない」、64-core-b3.asm の PUTSTR
  コメント）。つまり**文字列空間内のポインタ共有は起きない**のが
  インタプリタ全体の不変条件で、§2 の実測（TIES=0）もこれを裏付ける。

## 2. ワークロード実測（今回の計測）

### 2.1 方法

- GCPROF 計測ビルド：redesign ツリーの複製にカウンタフックだけを足した
  rd 変種（19,406 B、正本イメージには入れない）。カウンタは未使用の
  ミラー領域 $014000 に置き、emu 派生 emu_gc が終了時に読み出す。
  数えるのは：起動回数（起動者別）、移動文字列数（回収ごとの分布
  バケット付き）、GC_CHK 呼出総数、最終パスの走査数（＝D）、同点検出。
- ワークロードは M6 と同一条件（port/full.script、スロット6 preload、
  スロット5 dump）。キャップ付き2本：A＝計測71G、B＝計測223G。
- 注意：フック自体がエミュレーション・サイクルを消費する（実測較正で
  GC_CHK 1回あたり約67サイクル）。そのため到達点は TX バイト長を
  無計測ビルドの較正点（60G→119,448 B、223G→224,354 B）に当てて
  無計測換算した：A ≈ 57.7G 地点、B ≈ 177.2G 地点。差分スパン ≈
  119.5G（第1周の末尾約13.5G＋第2周の前半約106G）。
- 健全性：両ランの TX はゴールデン full.out の完全な前方一致（計測が
  ワークロードを変えていない）。test4 スモークでもバイト一致＋
  スロット5 46 B / sum 41273 を確認。

### 2.2 結果

| 項目 | 第1周（ランA、〜57.7G） | スパン（≒第2周） |
|---|---:|---:|
| GC 起動回数 | 291 | 294 |
| 起動者内訳 | **FRE 291 / GETSPA 0 / DIM 0** | **FRE のみ**（通算 585 回全て FRE） |
| 移動文字列数（合計） | 142,922 | 319,127 |
| 移動数／回 | 平均 491、最大 937 | **平均 1,085、最大 1,115** |
| 分布 | >512 が 139 回 | **294 回全て >512** |
| GC_CHK 総数 | 174,705,307 | 389,991,265 |
| D（1パスの走査数） | 1,220 | 1,221 |
| 同点（TIES） | 0 | 0（通算 564,696,572 判定で 0） |

導出値：

- **コストの正体は「少数の巨大な収集」ではなく「FRE 駆動の頻繁な
  全収集」**。ASM.BAS 本体 line 1210 が16行ごとに `GC=FRE(0)` を呼び
  （EhBASIC 期の文字列空間対策の名残）、1周あたり約345回（5,519行÷16）、
  毎回ほぼ全生存文字列（第2周で平均1,085件）を動かす。GETSPA 不足に
  よる収集は計測範囲で **0回** — FRE 学科が空間を常に詰めておくため
  不足自体が起きていない。
- D=1,221 の内訳は NM$(1200) の要素 1,201 件が支配的（＋単純変数
  約17件＋テンポラリ最大3件）。
- 判定1回あたりの実効コスト ≈ **270 ± 30 サイクル**（第2周窓の GC
  133.4G を同窓の判定数約4.9e8 で割る／スパン実測との交差確認済み）。
  絶対番地ロングアクセス主体の68Kコードとして妥当な値。
- 第2周の収集1回あたり GC コスト ≈ 133.4G ÷ 約345回 ≈ **約390M
  サイクル**。内訳は (1,085＋1) パス × 1,221 件 × 約270 ≒ 358M が
  探索、残りが BLTU 移動と出入り。
- 第1周も GC 支配的と推定される（判定総数約2.2e8 × 約270 ≒ 55–58G /
  70G、約8割）。S が周の進行とともに育つため第2周より軽い。
- フルラン 951.5G の分解（実測＋推定）：ロード 1.2 ＋ 第1周 70
  （GC 約55）＋ 第2〜6周 5×152＝760（GC 約667）＋ PASS 2＋SYM 約120
  （GC 占有率は未計測）。**GC 合計は約720–780G（全体の76–82%）**。

## 3. 候補設計

### C1（推奨）：作業リスト＋ソート＋一括スイープ — 移動順・最終配置は不変

探索だけを置き換える保守案。GARBAG の入口・出口の契約（FRETOP／
FRESPC の初期化、ディスクリプタその場更新）はそのまま。

1. **構築（1回の全走査）**：現行と同じ順序で所有者を走査し、候補
   （長さ＞0 かつ STREND ≦ ptr ＜ MEMSIZ）を作業リストに
   (データポインタ, ディスクリプタアドレス) の8バイト組で追加。
   コスト O(D)。
2. **ソート**：ポインタ降順に基数ソート（基数256、アドレスは19ビット
   幅なので3パス、ピンポン用に2倍のバッファ）。コスト O(S)。
3. **スイープ**：降順に1件ずつ、現行と**まったく同じ BLTU 移動**を
   同じ順序・同じ送信元/先/長さで実行し、そのディスクリプタだけを
   更新、FRETOP を進める。移動列そのものが現行と同一なので、最終
   配置どころか途中状態まで一致する。

- 複雑さ：**O(D ＋ S ＋ 生存バイト数)** / 回。
- 作業リストの置き場：rd レイアウトの未使用ミラー領域
  $011000–$017FFF（28 KB。ZP は $010334 まで、LTABLE は $00D000–
  $00FFFF、FN 表は $018000–$0182FF で、いずれとも衝突しない）。
  プログラム可視状態（FRE の値、変数・配列の配置）の外なので、
  リスト自体は観測不能。ピンポン込みで容量 1,792 件。実測の最大は
  1,115 件で余裕 1.6 倍。**容量超過時は現行 GARBAG 本体にフォール
  バック**（病理的に小さい文字列が数千件生きるプログラムでも正しさ
  は不変、速度だけ現行並みに戻る）。
- 唯一の意図的差異：同点（同一ポインタの複数ディスクリプタ）が
  万一存在した場合、現行の「後勝ち1件更新＋残りは破損」ではなく
  「1回移動して全共有者を更新」にする。§1.3 の通り共有は不変条件
  として起きず、実測でも 5.6e8 判定で 0 件。起きないはずの経路で
  現行より安全側に倒す差異であり、§5 のプローブで明示的に検証する。
- 予測（§2 の数値から）：収集1回 ≈ 構築 1,221×約70 ＋ ソート
  3×1,100×約25 ＋ スイープ 1,085×約60 ＋ BLTU 生存約12 KB×36
  ≈ **約0.7M サイクル**（現行 約390M の約1/550）。
  - 第2周：18.6（非GC）＋ 約345回×0.7M ≒ **約19G**（現行 152G）
  - 第1周：非GC 約15 ＋ 約0.1 ≒ **約15G**（現行 70G）
  - 第2〜6周：5 × 19 ≒ 94G。PASS 2＋SYM は GC 軽微と仮定して
    120G のまま（ここが最大の不確実項。GC を含めば更に縮む）
  - **フルラン予測 ≒ 230G（範囲 200–280G）**、現行 951.5G の
    約4.1倍速。6 MHz 換算 約10.7 時間、10 MHz で 約6.4 時間、
    Kyo の PC sim（持続 約78M/秒）で 約50 分、この VM
    （約240M/秒）で 約16 分。EhBASIC の 157.5G には届かないが
    差は 6.0 倍 → 約1.5 倍になる。
- 実装規模：約150–200 行（構築 約60、基数ソート 約70、スイープ
  約50、フォールバック糊 約10）＋ リスト基底の EQU 追加。
  マイルストーン2つ（実装＋単体ゲート／ボス・スライス再計測＋
  フルラン）。リスク：**低〜中**。等価性は「同じ移動列」で構成的に
  示せるため、主リスクはソート/スイープの簿記バグで、いずれも
  ゲートで捕捉できる。

### C2：非移動 mark-sweep ＋ フリーリスト（参考・非推奨）

生存文字列を動かさず、空きをフリーリストで再利用する方式。収集
コストは C1 並みに下がる（予測フルラン 230–260G 級）が、
プログラム可視の振る舞いが広く変わる：

- 文字列アドレスが GC をまたいで安定になる（現行は動く）→ VARPTR／
  PEEK で観測するプログラムには別物になる
- FRE の返り値が「断片化した空き合計」になる。空きがあるのに
  断片化で ?OM ERROR になる経路が新たに生まれる
- GETSPA の割当パターン（フリーリスト先頭適合）が変わり、以後の
  全文字列アドレスが現行とずれる
- FRETMP の「FRETOP 直上なら pop」最適化とフリーリスト末端の整合
  など、周辺部品の作り直しが要る

ボスの出力バイト一致は（アドレスを印字しないため）おそらく保てるが、
FRE 値に分岐するプログラム一般の意味が変わる。C1 がほぼ同じ利益を
配置不変で得られる以上、採る理由がない。実装規模 300 行超、
リスク：**高**。

### C3：ディスクリプタ・ディレクトリ＋現行探索の高速化（代替案）

移動列と探索規則（最大値・後勝ち）は現行のまま、所有者列挙だけを
高速化する中間案。全文字列ディスクリプタのアドレス一覧（ディレク
トリ）を DIM／変数生成／CLEAR 等で保守し、各パスは配列ヘッダの
再解釈や型判定なしにディレクトリを直線走査する。

- 判定1回の実効コスト 約270 → 約100 サイクル（見込み）。
  GC は約0.38 倍：第2周 約69G、第1周 約36G。
- **フルラン予測 ≒ 500G（範囲 460–560G）**、約1.9 倍速。
- 実装規模：約80–120 行＋保守フック約6箇所。リスク：**中**
  （ディレクトリの保守漏れ＝静かな破損経路になるのが主リスク。
  移動列が現行と同一な点は C1 と同じ強み）。
- C1 に対する利点は「ソートを持たない」ことだけ。利益が C1 の
  半分以下で、保守対象が増える分リスクは C1 より高い。

## 4. 推奨

**C1 を推す。** 理由：(1) 利益が最大（951.5G → 約230G）で、しかも
利益の源泉が「同じ移動列のまま探索だけを消す」ことに限定される
ため、等価性を構成で示せる。(2) 作業リストは可視状態の外に置け、
容量超過フォールバックで最悪ケースの正しさも現行に帰着する。
(3) R3（バイトコードVM）以降も文字列層はこのコレクタを使うので、
ここでの削減は梯子の残り全部に効く（R3 のボス予測 380–630G は
GC 88% 前提では崩れるが、C1 後の土台なら評価器側の削減がそのまま
効くようになる）。

段階：
- **M-GC1**：C1 を実装（GARBAG 入口は不変、探索部を置換＋現行本体を
  フォールバックとして残置）。単体ゲートを通す。
- **M-GC2**：ボス・スライス再計測とフルラン検証で受け入れ。

## 5. 検証計画

1. **スイート**：run_rd 233/233（emu／emu_strict 両方）。ASCIIART は
   ゴールデン・バイト一致＋サイクル記録（GC 占有が小さいため変化は
   ±2% 以内の予測）。
2. **等価性ハーネス（新規）**：既知の文字列集合で GC を強制し、
   内容・VARPTR アドレス・FRE 値を現行コレクタのゴールデンと
   照合する BASIC プローブ群を run_rd に追加。配列文字列、式の
   途中のテンポラリ、文字列 LET の共有系（PUTSTR コピー経路）、
   LEFT$/MID$ 結果、同点プローブ（共有を構成できる場合は現行との
   差異が §3-C1 の意図通りかを確認）を含む。
3. **test4**：トランスクリプト＋スロット5（46 B / sum 41273）
   バイト一致。
4. **ボス・スライス再プロファイル**：emu_prof で窓 [72G, 223G) を
   再計測。予測：GC 一族 88.31% → 5% 未満、第2周 約19G のため
   223G キャップでは第3周以降まで到達。TX は full.out の前方一致を
   維持すること。
5. **フルラン最終検証**：予測 約230G なら、この VM でも 約16 分で
   完走できる（無最適化の 約66 分から短縮され、VM ゲート化が現実的
   になる）。check_m6.py で判定（スロット5 13,788 B / sum 41893、
   SYMBOLS 1095、トランスクリプト 701,844 B バイト一致）。Kyo の
   PC sim での再確認は任意（約50 分の見込み）。
