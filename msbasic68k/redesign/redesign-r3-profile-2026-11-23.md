# R3 スコーピング用プロファイル — C1 ビルド / ボス・フルラン（2026-11-23）

問い：GC 修正（C1）後の MS-BASIC 68K で、ASM.BAS ボスの残り
125.25G サイクルは何に使われているか。R3（バイトコード VM）の
効果予測を、GC 前の古い地図（評価器 19.4%）ではなく実測で
置き直すための計測。Kyo の計画承認（2026-11-23、R2 受け入れと
同日）に基づく。

## 方法

- 対象：redesign rd ビルド（C1 入り）を再ビルドして検証
  （19,794 バイト / BSD sum 52171、C1 記録と一致）。
- ワークロード：M6 フルランと同一条件（port/full.script、
  boss-send5519.txt をスロット6に preload、スロット5 dump、
  最終 SYM 行 until）。今回は窓ではなく**フルラン全体**を
  プロファイルした（C1 で全長が 125.25G まで縮んだため可能に
  なった）。
- 手法：従来と同じ PC サンプリング。emu_prof で 1,000 サイクル
  刻みに実行し、各スライス末尾の PC をヒストグラム化
  （サンプル数 124,468,400）。rd リスティング（981 シンボル）の
  「直前のラベル」に帰属（排他時間）。
- ツール改修（記録）：emu_prof はスライス毎に until 文字列を
  全 TX 走査する実装で、1,000 サイクル刻みでは走査自体が
  支配的になり実用速度が出なかった（2G 到達に 120 秒超）。
  until チェックを 100,000 サイクル境界のみに間引く1箇所の
  改修を入れて再ビルドした（emu_prof.c、改修前は
  emu_prof.c.pre-r3 / emu_prof.pre-r3 に保存）。これにより
  2G スモークが 7.1 秒で完了し、TX はゴールデン前方一致、
  サンプル数はちょうど 2,000,000 を確認してから本番を実行。
- 公称軸の注意：1,000 サイクル刻みでは m68k_execute の
  オーバーシュートが公称に乗らないため、prof ランの until 到達は
  124,471,400,000（settle 込み）で、正典ランの 125,246,800,000
  に対し比 0.99381。これは従来の窓プロファイルにも同じく
  乗っていた方法上のバイアスで、シェア（比率）には影響しない。
  本記録のシェアはすべて prof ランのサンプル比、絶対サイクルは
  正典総量 125.25G 換算で示す。
- 検証：プロファイル実行時の TX はゴールデン full.out と
  **バイト一致**（701,844 B 全体）、スロット5 は
  13,788 B / sum 41893 一致、rc=0。
- 実行経緯：1回目の実行は VM のサービス再起動で 71G 地点で
  死亡（--progress のフラッシュにより途中 TX は保全され、
  ゴールデン前方一致を確認）。再実行で完走（wall 1,760 秒）。

## 結果4：フェーズ分割

--progress の（サイクル, TX バイト）点を 1G 刻みで取得し、
ゴールデンのフェーズマーカー TX オフセット（PASS 1 バナー
43,704 / PASS 2 バナー 585,662 / SYMBOLS 行 676,039 /
最終 SYM 行 701,834）で線形補間した。正典総量換算：

| フェーズ | サイクル | 比率 |
|---|---:|---:|
| ロード＋setup（PASS 1 バナーまで） | 1.00G | 0.8% |
| PASS 1（PASS 2 バナーまで） | 105.28G | 84.1% |
| PASS 2（SYMBOLS 行まで） | 18.21G | 14.5% |
| SYMBOLS ダンプ（最終 SYM 行まで） | 0.76G | 0.6% |
| settle | 0.003G | — |

補間誤差は ±0.5G 程度。C1 記録 §5 の残差見積もり
（PASS 2＋SYM ≈14G）より実測の PASS 2 は重く（18.21G）、
PASS 1 は軽い（105.28G vs 見積 110G）。以降は本実測を正とする。

## R3 効果予測（ボス・フルラン）

消せるプールをファミリ実測から積み上げる（比率はフルラン比、
削減率は VM 化で実際に消える割合の見積もり）。

| プール | 比率 | 保守 | 楽観 | 根拠 |
|---|---:|---:|---:|---|
| A. CHRGET＋トークナイザ | 12.90% | −10.97 | −12.26 | バイトコード化で RUN 時のテキスト走査は消える（85–95%） |
| B. 評価器 | 20.79% | −8.12 | −11.84 | 骨格部（FRM_*/EV_* ≈12.08%）の 60–80% ＋ ワーカーへのディスパッチ（PF/FE ≈8.71%）の 10–25% |
| C. ディスパッチ＋文走査 | 8.86% | −5.94 | −7.10 | ELSESCAN/REMH（3.01%）は全消し、FETCH/EXEC/FTGO（5.85%）は VM ディスパッチ化で 50–70% |
| D. 行ターゲット | 3.77% | −3.39 | −3.77 | ジャンプ先はコンパイル時にアドレス化（90–100%） |
| E. BRKCHK | 1.74% | −0.00 | −0.44 | VM でもポーリングは残る（0–25%） |
| F. PTRGET 名前解決 | 8.65% | −0.00 | −4.33 | 楽観側のみ：スカラーの事前解決（配列は変数追加でブロックが動くため対象外とする） |
| G. FAC 管理 | 6.16% | −0.00 | −1.85 | 型付きオペコードで FAC↔ARG 往復の一部が消える（楽観側のみ 30%） |
| **合計削減** | | **−28.42 pt** | **−41.59 pt** | |

予測：**フルラン 73〜90G**（C1 比 1.4〜1.7 倍）。
6 MHz 実機換算で 3.4〜4.2 時間（C1 は 5.8 時間、EhBASIC は
7.3 時間）。EhBASIC との差は現在の 1.26 倍から
1.75〜2.2 倍へ広がる計算になる。

留保：
- R3 は RUN 時にコンパイル代を払う（1,454 行規模なら
  ロード時の CRUNCH が目安で、ボス規模では誤差級だが、
  短いプログラムでは起動が僅かに重くなる）。
- 予測の前提は「VM が式と文の実行経路を置き換える」範囲で、
  FP コア・FP 変換・文字列演算の実作業は残る。特に
  FP 変換 12.77% と FP コア 7.90% は VM 化ではほぼ減らない。
- 今夜の教訓として：この種の外挿は過去2回外している
  （530G 予測、230G 予測）。本予測も帯域で読み、
  実装後に実測で確定させること。

## R3 以外のレバー（単独の天井つき）

1. **QINT 高速化**（天井 約7.3 pt、現実的には −3〜3.5 pt）：
   QINT 一族 5.65%＋FAC32I 1.69%。QINT_RL 単独で全体2位。
   添字・DOKE/POKE 引数・整数演算の境界で FP→int32 変換が
   繰り返し走っている。小さい整数の近道（範囲内チェックで
   一般経路を回避）を置く余地がある。
2. **FIN 高速化**（天井 4.87 pt、現実的には −2〜2.5 pt）：
   数値リテラルのパース。R1 のリテラルキャッシュ後も
   FIN_HIT だけで 0.96% ある。整数リテラルの INT 直接変換と
   キャッシュヒット経路の軽量化が候補。
3. **FNDBS のヒント化**（天井 2.23 pt、現実的には −1.5〜2 pt）：
   GOTO/GOSUB のたびに行テーブルを二分探索している。
   前回ヒット行からの開始（局所ジャンプが多い ASM.BAS では
   効く）で大半を消せる。インタプリタ内の小改修で済む。
4. **GC のダーティフラグ**（天井 約2.6 pt）：
   C1 後も FRE(0) のたびに D=1,221 件の走査＋ソートが走る
   （GN_S 0.91%＋GC_ADD 0.71%＋GN_C 0.46%＋GN_W1 0.33%＋
   GN_AE 0.23%）。「前回収集以降ゴミが増えていない」場合は
   FRE が収集を丸ごと省略できる。フラグの立て方
   （FRETMP／PUTSTR の解放と GETSPA のゴミ生成で立てる）の
   設計が要るが、効果は FRE 学科のある全プログラムに効く。
5. **VH_LOOK の軽量化**（天井 2.27 pt、現実的には −1 pt）：
   ハッシュ表の拡大または衝突歩行の短縮。
6. **ELSESCAN**（1.87%）：R3 で消えるので単独対策は
   使い捨てになる。やらないのが無難。

## ASCIIART について（再計測なし）

M9 プロファイルで FP 複合体 50.6% と FP 支配が確定しており、
C1 前後でサイクルは完全一致（883,200,000、GC 占有ゼロ）。
ASCIIART の地図は本計測とは別物で、R3 の効き方も
ボスとは異なる（評価器経由の FP 演算が中心）。必要になったら
別途プロファイルすること。
