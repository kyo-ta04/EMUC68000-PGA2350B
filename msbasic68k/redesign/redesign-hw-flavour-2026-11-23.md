# 再設計 hw フレーバー（rdhw）— 監査・ビルド・sim 検証記録（2026-11-23）

実機統合ステップ1：受け入れ済み再設計（R2+C1、rd = 19,794 B /
BSD sum 52171）を、デュアルブート（→トリプルブート）ファームの
常駐イメージとして載せるための監査と、hw フレーバー `rdhw` の
ビルド＋sim ゲート。ファーム再ビルド／書き込みは対象外（ステップ2）。

## 結論サマリ

- **ブロッカー 0 件。** 再設計の A1 レイアウトは R0 設計時点から
  ボードのマップそのもの（redesign-r0-design.md §1）であり、
  常駐ルートに必要なレイアウト変更は存在しなかった。
- `rdhw` は rd と**バイト完全一致**（19,794 B / sum 52171）。
  フレーバーの実体は「ファーム向けの固定ピン付きパッケージ」であり、
  build.py がサイズ／sum をピン留めして rd との静かな乖離を防ぐ。
- ゲート全通過：run_rdhw **233/233（emu／emu_strict 両方）**、
  ASCIIART golden 一致（セッション 883,200,000 サイクル、rd と同一）、
  test4 **合格**（トランスクリプトが R1 ゴールデンとバイト一致、
  slot5 46 B / sum 41273、1,195,100,000 サイクル＝C1 版 rd と同一）。
- 作業前後で `build.py rd` は 19,794 / 52171 のまま不変
  （純追加変更のみ）。

## 1. 監査表

前提の確認：sim（emu.c の RAMMASK $3FFFF）とファーム
（EMUC68000-PGA2350B.c の MEMADRS_MASK $3FFFF、memory[262144]）は
同じ 256KB ミラー・バスモデル。ファームのブートメニューは
`load_to_memory(image, size, 0x0000)` でイメージを 0 番地へ置く
だけで、ベクタ書き換えやメモリマップ上の要求は一切課さない。

| # | 再設計側の前提 | ボード／ファームの実態 | 判定 |
|---|---|---|---|
| 1 | イメージは $0 配置、自前リセットベクタ | ローダは $0 へ置くだけでベクタはイメージ内蔵値を使用（phase1 常駐で実証済み） | そのまま |
| 2 | エントリ PC = INIT $0001B2（ベクタ経由） | ローダ側のエントリ修正なし | そのまま |
| 3 | 初期 SSP = $040000（256KB の 1 つ先） | バスは & $3FFFF でマスクされ、最初のスタックアクセスは $3FFFC に落ちる。sim と同一モデルでフルラン実証済み。ファームは SSP に何も要求しない（phase1 の $030000 は phase1 自身の sizing であって要件ではない） | そのまま |
| 4 | コード 19,794 B、コード終端 $04D52 | 配列は const（FLASH XIP 常駐）。load_to_memory の上限は MEMORY_SIZE 262,144 のみ | そのまま |
| 5 | ZP $010000、INIT で $0332 バイト消去 | RAM 内。消去規律は INIT/SCRATCH 内蔵 | そのまま |
| 6 | 変数ハッシュ VHASH $008000（4KB） | SCRATCH/CLEARC で VH_CLEAR が全消去 | そのまま（ゼロ初期化 RAM への依存なし） |
| 7 | リテラルキャッシュ LCACHE $00C000（4KB） | SCRATCH/CLEARC/STORE で LC_CLEAR | そのまま |
| 8 | 行表 LTABLE $00D000–$00FFFF（2,048×6B） | 有効性は ZP 内 LTVALID で管理し RUN 時に再構築 | そのまま |
| 9 | GC-C1：GCCTAB $010E00、ワークリスト $011000–$017FFF | GCCTAB は各基数パスでゼロ化、リストは書いてから読む。領域は ZP 終端〜FNTAB の間の非公開領域（FRE/CLEAR の計算外） | そのまま |
| 10 | FN 表 FNTAB $018000（64×12B） | 走査は ZP ポインタ FNTOP が境界。未初期化の表内容は読まれない | そのまま |
| 11 | TXTTAB $020000 / MEMSIZ $03F800 → BYTES FREE 129,024 | ユーザ空間は着陸ゾーン $30000–$3FFFF を含むが、常駐時は EhBASIC は不在で、起動後に 68K RAM へ書く者は他にいない（テープ／ACIA はレジスタデバイス） | そのまま（下記注記） |
| 12 | スタック予約 $03F800–$03FFFF（2KB） | R0 設計通り。ビット同一な sim でボス完走実証済み | そのまま |
| 13 | コンソール ACIA $80E000/$80E001（フルアドレスデコード） | 50-machine.asm は phase1 と**バイト完全一致**＝Stage B で実機検証済みの層そのもの | そのまま |
| 14 | テープデバイス $80E100（RDLNUSR の論理 $7FE100） | sim のデバイスはファーム自身の tape-device ブロック（step4/tape-device-4a.inc.c）の移植。インタプリタ側は USR/PEEK/POKE のみ | そのまま（製品ファームへの同ブロック含有確認はステップ2/3 の確認事項） |
| 15 | USR カーネル配置 論理 $F000 → 物理 $1F000 | FNTAB 終端（$018300）と TXTTAB の間の空き RAM | そのまま |
| 16 | 起動時 RAM 内容 | ファームの memory[] は静的配列＝ゼロ初期化。加えて上記 5–10 の通り全ての副領域が消去／境界／使用前ゼロ化で守られている | そのまま |
| 17 | クロック（現行 1MHz 等） | ファーム側定数で両ブート経路共通。イメージの性質ではない | 対象外 |

注記（#11 の帰結）：常駐 rd の下では EhBASIC 時代の
「$30000 は USR カーネルのために空いている」という慣習は成り立たない
（ユーザ空間の一部）。常駐用の USR カーネルは別所（例：コード終端
$04D52–$007FFF の約 12.6KB の空き）に置くこと。これはイメージの
欠陥ではなくステップ3 の配置規約の話。

集計：**そのまま 16 件／要調整 0 件／ブロッカー 0 件**
（#17 はイメージ対象外、#14 にステップ2/3 確認事項 1 件）。

## 2. 常駐レイアウトの決定：再設計ネイティブ（BYTES FREE 129,024）を採る

phase1 常駐の BYTES FREE 61,440（MEMSIZ $02F000）は、phase1
インタプリタ自身の sim 設定値であり、ローダ／ボードの要件ではない
（§1 の通りローダはマップを課さない）。再設計を 61,440 に
絞ることは、A1 が解消するために作られた「ASM.BAS が入らない」
問題の再導入になる：ボスのテキストだけで 46,478 B あり、
R1 実測では 129,024 の空間でプログラム格納＋実行が成立している。
よって常駐ビルドは再設計ネイティブのレイアウト
（MEMSIZ $03F800、初期 SSP $040000、BYTES FREE 129,024）で統治する。

## 6. トリプルブート実現性（Kyo 追加スコープ、2026-11-23）

対象：EhBASIC（既定）／phase1 コンマ NEXT 修正版 MS-BASIC／
再設計 R2 の 3 択。

### 現行デュアルブートの実態（ファームソース確認）

- 常駐イメージは `msbasic68k.c/.h` の C 配列 `MSBASIC68K[]` /
  `msbasic68k_size` として FLASH に埋め込み（ehbasic.c と同じ流儀、
  `gen_msbasic68k.py` で生成）。
- メニュー `boot_menu_msbasic_selected()`（main 直前）が USB CDC を
  3 秒待ち、'M'/'m' で true、それ以外／タイムアウトで false。
- main() は分岐で**どちらか一方の** `load_to_memory(..., 0x0000)`
  だけを実行してから bus_emu 起動・RESET 解除へ進む。
  → **同時に常駐するイメージは常に 1 つ**。RAM 配置の競合は
  構造的に存在しない（3 イメージとも $0 配置・自前ベクタで、
  使い回すのは同じ memory[262144] の先頭）。
- サイズ上限は load_to_memory の MEMORY_SIZE クランプのみ。

### 判定：実現可能、ブロッカーなし

- **FLASH 予算**：EhBASIC 16,384 B ＋ phase1 ext-sim 現行ビルド
  16,536 B（今回実測、sum 25401）＋ rdhw 19,794 B ＝ **52,714 B**。
  16MB FLASH の約 0.3%。ファーム本体コードに対しても無視できる増分。
- **RAM**：上記の通り競合なし。イメージ配列は const で FLASH 常駐、
  SRAM を食うのは memory[256KB] のみ（現行通り）。
- **メニュー／ローダ変更**：キー 1 つ追加（'R'）と 3 分岐化のみ。
  既定（タイムアウト／'E'）＝EhBASIC の挙動は不変。

### ステップ2 のファーム側変更リスト

1. 配列を 2 本生成する。`gen_msbasic68k.py` は ARRAY_NAME と
   出力ファイル名が固定なので、名前／サイズシンボル／出力名の
   パラメータ化（または複製）が要る：
   - `MSBASIC68K` ← phase1 ext-sim **現行ビルド** 16,536 B / sum 25401
   - `MSBASIC68K_RD` ← redesign rdhw 19,794 B / sum 52171
2. **注意：現行埋め込みの phase1 配列（16,530 B / sum 32550）は
   コンマ NEXT 修正前**。トリプルブート化の際に上記現行ビルドで
   再生成すること（でないと NEXT 修正が実機に載らない）。
3. `EMUC68000-PGA2350B.c`：第 2 ヘッダの include 追加；
   `boot_menu_msbasic_selected()`（bool）を 3 択（enum/char）に
   変更しメニュー文言を更新；main() の分岐に 'R' 経路
   （`load_to_memory(MSBASIC68K_RD, msbasic68k_rd_size, 0x0000)`）
   を追加。既存コメントの「SSP=$00030000, PC=$00000194」は
   phase1 イメージ固有値なので R 経路では書き分ける
   （rdhw は SSP=$040000、PC=$0001B2）。
4. `CMakeLists.txt`：第 2 のイメージ .c を add_executable に追加。
5. ベンチ予測の更新：'M' → `61440 BYTES FREE`（不変）、
   'R' → §5 のトランスクリプト（`129024 BYTES FREE`）。
6. （ステップ3 寄り）実機テープ経路が要るなら、製品ファーム
   ツリーに tape-device ブロック（$80E100）が含まれるか確認する。

### 対象形式の結論

- **常駐 $0 イメージ（ブートメニュー用）を本線とする**——これが
  トリプルブートの要る形式であり、rdhw はそれを満たす。
- **$30000 CALL ルートは作らない（設計上の却下）**：phase1 の hw
  フレーバーは EhBASIC 常駐＋着陸ゾーン（BYTES FREE 40,960）の
  前提で成立しているが、再設計の A1 は絶対番地の副領域
  （$008000–$017FFF）とユーザ空間（$020000–$03F800）が
  EhBASIC の常駐ワークスペース（ram_size $28000）と全面衝突し、
  ゾーン内 40,960 B ではボスのテキスト（46,478 B）すら入らない。
  CALL 版は設定変更ではなく別メモリモデルになる。R0 §1 の
  「再設計版の配布はファーム統合が前提」という割り切り通り。
