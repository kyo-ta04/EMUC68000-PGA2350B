| ゲート | 結果 |

| `python3 build.py rd` | **PASS** — 18,462 バイト / BSD sum 6438（R2-M1 時点 18,034 / 41803、+428 バイト） |

サイクル増の主因の見立て：評価器フレーム拡張（EV_RECURSE 毎の FACINT ロング＋FACTYP ワードの push/pop）とラッパ経由のディスパッチ。速度は R2 の合否ゲートではない（決定ファイル通り、計測・記録のみ）。

## フレーム拡張（parts/60-core-b.asm）

- `EV_RECURSE`：FAC 5 バイトの後に **FACINT（ロング）＋FACTYP（ワード）** を積む。ロング＋ワードの組なので、この地点以降の push 列（および PERFORM2 の pop 列）は偶数境界を維持する（それ以前の FACSIGN バイト push を含む既存列は従来通り）。
- `PERFORM2`：マスクワードの直後に FACTYP ワード→**ARGTYP**、FACINT ロング→**ARGINT** を復元する。CPRTYP には一切触らない（2026-11-22 の PERFORM2 バグの教訓：保留中の関係マスクを壊さない）。フレームを pop するのは PERFORM2 だけであることを監査済み（CAT は EV_OPDEC から直接分岐し、自前のバランスした push/pop のみで EV_OP に戻る。STOP/CONT はフレームを保存しない＝式の途中では止まらないので無変更）。

## クリア規律の再編（PERFORM2 の一律クリアを撤去）

PERFORM2 末尾の `CLR.B FACTYP`（M1 のチョークポイント）を削除し、各演算子が自分の結果の型に責任を持つ形にした：

| 演算子（MATPERF） | 実体 | INT 時の振る舞い | FP 時の FACTYP |
|---|---|---|---|
| + | **IADD**（新規ラッパ）→ FADD_CORE | 両辺 INT なら ADD.L、V で溢れ検出 | FADD_CORE 頭でクリア |
| − | **ISUB**（新規ラッパ）→ FSUB_CORE | 両辺 INT なら ARGINT−FACINT、V 検出 | FSUB→FADD_CORE 頭でクリア |
| * | **IMULT**（新規ラッパ）→ FMULT_CORE | 両辺 INT なら IMUL32（下記） | FMULT_CORE 頭でクリア |
| / | FDIV_CORE（直接） | 常に FP（D2） | FDIV_CORE 頭でクリア（新規） |
| ^ | FPWR（直接） | 常に FP（D2） | FPWR 頭でクリア（新規） |
| AND | **IAND**（新規ラッパ）→ TAND | 両辺 INT なら int32 ビット AND | 従来 AYINT 16 ビット経路、結果は GIVAYF がクリア |
| OR | **IOR**（新規ラッパ）→ ORPERF | 両辺 INT なら int32 ビット OR | 同上 |
| 単項 − | **INEGOP**（新規ラッパ）→ NEGOP | FACINT を否定して INT 維持。-(-2147483648) は FP 昇格 | NEGOP は純粋な符号反転のまま（下記） |
| NOT | **INOT**（新規ラッパ）→ EQUOP | FACINT のビット反転、INT | 従来 AYINT 経路、GIVAYF がクリア |
| 関係 | RELOPS（直接、無変更） | FP シャドウ同士の FCOMP で値比較（下記） | 結果は FLOAT_BYTE 経由で FP -1/0（従来通り） |

ラッパ方式にした理由：FADD_CORE 等の FP コアは内部 FP コード（FMUL10、FADDH、FOR/NEXT のステップ加算、数値パック）からも直接呼ばれ、そこでは ARGTYP は無意味。整数ディスパッチは PERFORM2 が復元した ARGINT/ARGTYP を見られるラッパにだけ置き、コア側は「頭で FACTYP をクリアする」ことで直接呼び出しでも結果の型が正しくなる。

**NEGOP 本体は無変更**：INPFIN が「FACINT を先に否定してから NEGOP に入る」経路を持つため、NEGOP が INT を触ると二重否定になる。単項マイナスの INT 化は INEGOP ラッパ側で完結させた。

## 乗算の溢れ検出（IMUL32、parts/60-core-b.asm）

MULU は 16×16→32 しかないので、符号なし大きさの 16 ビット部分積から 64 ビット積を組み立てる：a = ah·2¹⁶+al、b = bh·2¹⁶+bl として |a·b| = p0 + (p1+p2)·2¹⁶ + p3·2³²（p0=al·bl、p1=al·bh、p2=ah·bl、p3=ah·bh）。上位ワード（ビット 32..63）を別途蓄積し、溢れ判定は「上位ワード ≠ 0」または「符号に対する下位ワードの限界超過」（正は < 2³¹、負は ≤ 2³¹）。大きさで計算するので -2147483648（大きさ 2³¹）も安全。シフトは #8 を2回（#16 はエンコード不可）。検証は境界ケースで実施：46340² = 2147395600 は INT、46341² は FP 昇格、65536² は FP 昇格、2147483647×1 は INT、-2147483648×-1 は FP 昇格（プローブ＋スイート）。

## 関係演算の正確性（無変更の根拠）

int32 は全て FP シャドウで厳密に表せる（仮数 32 ビット）ため、既存の FCOMP（パック済み ARG 対 FAC）による比較は値として厳密。境界で確認：2147483647 対 2147483646（仮数が $FFFFFFFE 対 $FFFFFFFC で別値）、2000000000 < 2000000001 → 真、2000000000 < 2000000000.5 相当の混合比較（5 < 5.5 で代表）も真。結果の型は従来通り FP の -1/0（観測可能な振る舞いを変えない）。文字列比較（STRCMP／CPRSTR）と CAT はバイト単位で無変更で、スイートの文字列・関係マトリクス（-1<1、2^3<9 を含む）が全通過。

## 新規チェック（run_rd.py、SESSION の R2-M2 節、25 件）

FP 昇格ケースの期待文字列は、実装前に現行（M1）ビルドをプローブして採取した FOUT バイト列そのもの（` 2.14748365E+09 `、` 4E+09 `、` 1E+10 ` 等）。

- INT 結果：100000*3、1000*1000、46340²、30000² の代入、-2147483647-1（INT -2³¹ ちょうど）
- FP 昇格（D3）：2147483647+1、2000000000+2000000000、A%=-2147483648 での A%-1、46341²、65536²、A=100000 での B=A*A（代入時の昇格）
- 単項 −／NOT：-A%（A%=5）、-(-2147483648) の昇格、NOT 0 → -1、NOT 5 → -6
- AND/OR：2000000000 AND 2000000000（M1 では ?IQ だった）、16777216 OR 255 → 16777471
- 関係：2000000000<2000000001、2147483647=2147483647、5=5.0、5<5.5、2147483647<2147483646 → 0
- / は FP のまま：PRINT 7/2 → ` 3.5 `、A%=7/2 → 3（M1 の STO_INT32 チェーン）

## asm68k-py 拡張

**なし**。新規に必要だった命令形式（AND.L／OR.L／NOT.L／ADDX.L／BVS／SUB.L／CMPI.L #imm,Dn 等）は全て既存エンコーダで通り、ビルドとプローブで意味まで確認できた。したがって `asm68k-py-extensions.md` は作成していない。自己アセンブル監査への影響もなし（使用ニーモニックは従来のサブセット内）。

## 先送り・既知事項

- \ と MOD、整数 FOR（D4）は M3。現状 FOR % は ?SN のまま。
- D6（PEEK/DEEK/LEEK の INT 返却、SGN/ABS/INT の型規則）と VAL の INT 化は M4。INT 関数は現状 FP 経路（値は従来通り）。
- INT 0 の劣化（SFLOAT32 の 0 は FP 0）は M1 からの既知事項のまま（観測同一）。このため 0 を含む整数演算は FP 経路に落ちることがあるが、値と表示は同一。
- 混合 AND/OR（片方 FP）は従来の 16 ビット AYINT 意味論を厳密に維持：例 `70000 AND 3.5` は M1 と同じく ?IQ（プローブで確認）。
