# GC-C1 実装結果 — MS-BASIC 68K R2（2026-11-23）

設計検討 redesign-gc-design-2026-11-23.md の候補 C1 を実装し、
GC-M1（実装＋単体ゲート）と GC-M2（ボス再プロファイル＋フルラン）
の全ゲートを通した記録。Kyo の C1 実装承認（2026-11-23）に基づく。

## 結論

- **フルラン 125,246,800,000 サイクル**（旧コレクタ 951,543,900,000
  の **7.6 倍速**）。トランスクリプトはゴールデンとバイト一致、
  スロット5 13,788 B / sum 41893、SYMBOLS 1095。
- 予測（中央 ≈230G、範囲 200–280G）は外れたが**速い側**に外れた。
  原因は §5 に分析。
- 観測可能な振る舞いの変化は、同点（共有ポインタ）の意図的差異
  ただ1つ（§4 タイプローブ）。それ以外は全ゲートでバイト一致。

## 1. 実装

対象：redesign/parts/64-core-b3.asm の GARBAG、
redesign/parts/20-equates.asm の EQU 追加。

- **GARBAG 入口**：FRETOP/FRESPC 初期化の後 `BSR GCNEW` し、
  D0=0 なら終了、D0=1（作業リスト溢れ）なら従来コレクタ本体
  （GB_FIND 以降、無変更で残置）にフォールバック。
- **GCNEW（C1 本体）**：
  - 構築：従来の3走査（テンポラリ／単純変数／配列要素）を同形に
    再現し、GC_CHK の代わりに GC_ADD で候補（長さ>0 かつ
    STREND ≦ ptr ＜ MEMSIZ）を作業リストへ走査順に追加。O(D)。
  - ソート：安定 LSD 基数ソート（基数256、ポインタの下位3バイト、
    ピンポン2面）。同点グループ内は走査順が保たれるので、
    スイープが最初に出会う要素が原典の勝者（後勝ち）になる。O(S)。
  - スイープ：降順に原典 GB_MOVE と同じ BLTU 移動・同じ宛先規則
    で1回だけ動かし、ディスクリプタをその場更新。同点グループは
    1回の移動で全共有者を更新（唯一の意図的差異）。O(S＋生存バイト)。
- **作業領域**（プログラム可視状態の外）：
  GCLIST $011000–$017FFF（8バイト組×1,792件×2面、EQU GCLCAP）、
  基数表 GCCTAB $010E00（256ワード）。ZP スクラッチ
  GCCNT/GCAPP/GCOVF は ZPBASE+$340/$344/$348。
- **レジスタ契約**：原典 GARBAG と同一に保った。DIM 経路が D3 を
  保持して呼ぶため、C1 が余分に使う D3/D6/D7/A3/A4 は GCNEW 内で
  保存・復元する（使うのは原典が壊してよいレジスタ＋この5本のみ）。
- **イメージ**：19,148 B / sum 49995 → **19,794 B / sum 52171**
  （+646 バイト）。
- asm68k-py の拡張は**不要だった**（索引付き ADDQ/MOVE、
  LEA 負変位など使用した形式はすべて既存対応）。

## 3. タイプローブ（意図的差異の検証）

前提の実測による確定：文字列空間内の同点は純粋な BASIC からは
作れない（代入は PUTSTR がデータをコピーし、リテラル代入は
プログラムテキスト内ポインタ＝STREND 未満で収集対象外）。
そこで LEFT$ で作った文字列空間の2ブロックに対し、LEEK/LOKE で
ディスクリプタ手術をして同点を構成した（共有ブロックの上に
犠牲ブロックを置いて死なせ、共有ブロックが天井に接しない
配置にしてある）。

- 旧：勝者（後走査）だけ更新され、残りは旧ポインタのまま
  再移動される → ディスクリプタは分離（260024 / 260060）、
  共有ブロックは二重に詰められる（FRE が 36 小さい）。
- C1：1回の移動で両ディスクリプタが同一宛先に更新され、
  FRE は共有ブロックを1回だけ数える（FRE 差はちょうど +36）。
- 内容は両ビルドとも無傷。コントロール（同点なし）は
  旧新バイト一致。

## 5. 予測の検証（230G 予測 vs 実測 125.25G）

検討 §3-C1 のフルラン予測 ≈230G（範囲 200–280G）に対し実測は
125.25G で、帯域の下に 75G ほど外れた（速い側）。分解すると：

- PASS 1 側は検討の見積もり（第1周 ≈15G、第2〜6周 ≈19G×5）と
  ほぼ整合する（ロード 1.2＋15＋95 ≒ 111G）。
- 外れの主因は **PASS 2＋SYM**：検討は「GC 軽微と仮定して 120G
  のまま」と置いた（検討自身が最大の不確実項と明記）が、実態は
  この区間も FRE 駆動の GC が支配的だった。ASM.BAS の
  `GC=FRE(0)`（16行ごと）は PASS 2 とシンボル出力でも同様に
  走るためで、旧ビルドの同区間 約120G のうち約106G が GC
  だった計算になる（125.25 − 111 ≒ 14G が C1 後の同区間）。
- 教訓：このワークロードでは「GC が軽い区間」は存在しない。
  FRE 学科が全区間を貫いている。

6 MHz 実機換算では 125.25G ≒ 5.8 時間（旧 44.1 時間）。
EhBASIC の 157.5G との差は 6.0 倍 → **約 1.26 倍** まで縮んだ
（検討の見立て 1.5 倍より更に近い）。

## 6. 実装中の発見・逸脱

1. **ZP 衝突を実装中に検出**：GC スクラッチを当初 ZPBASE+$334 に
   置いたが、同アドレスは EXT1 の USRVEC（70-ext1.asm 定義、
   20-equates.asm 側の走査では見えない）。全パート横断の占有
   走査で検出し、$340/$344/$348 に移設した。最終配置は衝突なし。
2. フォールバック経路は「原典コレクタを無変更で残す」ことで
   実装し、fallback_over プローブで同コスト・同出力を確認した。
3. 検討 §5 の等価性ハーネスは run_rd 本体ではなく独立スクリプト
   run_gc_equiv.py として実装した（run_rd の 233 件ゲートを
   汚さないため）。中身は検討の指定通り。
4. redesign ツリーの faithful sim/hw ビルドは本変更前から
   壊れている（UFLOAT 未解決。rd が唯一のゲート対象）ことを
   変更前に確認した。本変更による退行ではない。
