# M7 結果メモ ― 拡張フェーズ第1バッチ（EXT1）

2026-11-19。対象：&H リテラル、USR 実働化、DEEK/DOKE/LEEK/LOKE、INSTR、ELSE。
方針は Kyo の原則「MBASIC そのまま」：形式・意味論は MS Extended BASIC（CoCo）を
参考にし、コードは全て独自実装（Searle / MS 6809 コードの転用なし）。
EhBASIC 方言（$ リテラル、1文分岐 ELSE）は持ち込んでいない。

## 結論

- **全ゲート合格**：`run_ext1.py` が **132/132 checks PASS**（通常 emu）、
  さらに `MSB_EMU=emu_strict` でも **132/132 PASS**。
- **忠実フレーバーは無傷**：パート分割後の結合ソースは M6 時点の生成物と
  **テキスト自体がバイト同一**で、バイナリも従来通り
  sim 15,492B / BSD sum 32584、hw 15,500B / sum 5542。
- 拡張フレーバー：**ext-sim 16,526B / sum 33635**、**ext-hw 16,534B / sum 12581**
  （いずれも忠実版 +1,034B）。
- ASCIIART は ext-sim / ext-hw / ext-hw-strict の全てで golden とバイト一致。
  拡張フレーバーでも既存スイート（run_m5d カスケード）が従来通り
  116/118（既知の 1-ulp 2件のみ）で通過＝拡張が既存挙動を変えていない証明。

## ビルド方式

asm68k-py に条件付きアセンブルが無いため、フック箇所を「忠実／拡張」の
**パート対**に切り出し、拡張専用コードは新パート `70-ext1.asm` に集約した。
`build.py` にフレーバー target を追加（`sim` / `hw` / `ext-sim` / `ext-hw`、
引数なしで全ビルド）。忠実側パートは原文とバイト同一テキストを同順序で配置。

パート対（9組）：41-reslst（キーワード表尾）、43-init（INIT 先頭）、
45-crunch（CRNNORM 先頭）、47-fetch（FETCH ディスパッチ検査）、
48-excol（EXEC の文終端検査）、49-if（IFH 全体）、4B-print（PRINT の
アイテムループ終端）、61-fevar（FE_VAR）、63-feu3（FE_U3）。
トークンは末尾追加のみ：DEEK=$CC、DOKE=$CD、LEEK=$CE、LOKE=$CF、
INSTR=$D0、ELSE=$D1（GO=$CB の後）。既存トークン値は不変。

## 各項目の意味論と判断

### 1. &H 16進リテラル
- 形式：`&H` の後に16進 1〜8 桁（大文字 A–F のみ。ポートのキーワードは
  大文字のみの慣例に合わせた）。0 桁、9 桁目は **?SN ERROR**。
- 値は**符号なし**：32767 以下は整数経路（GIVAYF）、超えたら符号なし32ビットを
  正確に浮動小数化（新設 UFLOAT）。`&H8000` = 32768、`&HFFFFFFFF` = 4294967295。
  CoCo の16ビット符号付き解釈を採らない理由：こちらのアドレス値は $30000 級が
  普通で、負数に化けると実用にならないため（タスク指定の判断をそのまま採用）。
- CRUNCH 対策：`&HDEF` が DEF、`&HEND` が END にトークン化される事故を防ぐため、
  CRUNCH の通常状態で `&`＋`H` を見たら16進数字列を**そのままコピー**する
  （CRNAMP）。評価側は FE_VAR フック → FE_HEX。終了契約は FIN と同一
  （A6/D0 は終端文字）。
- `VAL("&H..")` は対象外（VAL は FIN 経由で &H を解釈しない。CoCo の VAL も同様）。

### 2. USR 実働化
- 原典（m6502.asm）の機構に倣う：引数は FAC、呼び出しは RAM ベクタ経由、
  結果はルーチンが FAC に残したもの。ベクタは **USRVEC = ZPBASE+$334** の
  ワード（論理アドレス）。文字列引数は ?TM ERROR（FE_UFN の CHKNUM）。
- 未設定（ベクタ=0）は **?FC ERROR**：原典はベクタ初期値そのものが FCERR
  ルーチンのアドレス（`USRLOC: ADR(FCERR)`）なので、未設定 USR は原典でも
  FC を出す。ポートには GETADR や MID の「FC→IQ 写像」先例があるが、USR に
  ついては原典の機構が文字通り FC を指すため、EXT1 に実 FCERR スタブを新設して
  そちらを使った（タスク指定「?FC ERROR 相当」の文字通りの解釈）。
- ベクタは ZPSIZE の外（$334）に置き、NEW では消えない（原典の RAM ベクタと
  同じ）。ただし実機ルートでは着陸ゾーンの残留バイトがあり得るため、EXT 版
  INIT がコールドスタート時に明示的に 0 クリアする。
- 呼び出し規約：**A0 = FAC のアドレス**で JSR、RTS で復帰。ルーチンは
  FAC と FACSIGN の所有者になる。

#### ホスト側の設定手順（USR ベクタの書き方）
1. ルーチンのバイト列を論理ページ内に POKE する（例：論理 $6000 = 24576 番地）。
2. ベクタを書く：**論理 $334（=820）に上位バイト、$335（=821）に下位バイト**。
   例（ルーチンが $6000）：`POKE 820,96: POKE 821,0`（96 = $60）。
   EhBASIC からでも MS-BASIC からでも、論理ページは同じなので同じ手順。
3. `PRINT USR(引数)` で呼び出す。未設定のまま呼ぶと ?FC ERROR。
- テストで使ったルーチン：恒等 = `RTS`（$4E75）のみ。定数 2.0 を返す版は
  (A0) 相対のバイト書き：`10 BC 00 82`（MOVE.B #$82,(A0)＝指数）、
  `11 7C 00 80 00 01`（MOVE.B #$80,1(A0)＝仮数最上位）、
  `42 28 00 02`〜`00 06`（CLR.B 2..6(A0)＝仮数残り・FACOV・FACSIGN）、`4E 75`。

### 3. DEEK/DOKE/LEEK/LOKE
- アドレス変換は PEEK/POKE の GETADR を完全共有（範囲外の扱いも同じ ?IQ）。
- 値は**符号なし**：DEEK は 0..65535（PEEK の符号なし、EhBASIC の DEEK
  ゼロ拡張と整合）、LEEK は 0..4294967295（FAC に正確に入る）。
- DOKE の値は 0..65535（外れたら ?IQ、GETBYTE の鏡像 GETWORD）。
  LOKE の値は 0 ≤ v < 2^32（負、または指数 >160 は ?IQ、QINT で正確に変換）。
- **奇数アドレスでも壊れない**：語／長語の読み書きは全てバイト組立・バイト
  ストア（ビッグエンディアン）。ポート自身の奇数アクセス禁止規律を
  ユーザアドレスに対しても守るので、実機でアドレスエラーにならない
  （emu_strict 全スイート合格がその証拠）。
- 複数バイトアクセスは物理的に線形：論理ページ端を跨ぐと物理的に続く
  領域へ出る（テストはページ内境界まで。PEEK/POKE と同じ性質）。

### 4. INSTR
- 形式：`INSTR([開始位置,] 対象$, 探す$)`、1始まり、見つからなければ 0。
- 細部（MS Extended の流儀）：対象が空 → 0。開始位置 > 対象の長さ → 0。
  **探す文字列が空 → 開始位置を返す**（開始位置 ≤ 対象長の場合）。
  探す方が残りより長い → 0。
- 開始位置 < 1 は **?FC ERROR**（MS Extended の流儀。新設 FCERR を使用）。
  開始位置 ≥ 32768 は AYINT の ?IQ（ポートのワード変換規律に従う割り切り。
  文字列長は最大255なので実害はない）。
- 実装は FE_MID の作法（値をスタックに退避してから評価、ディスクリプタは
  直接読む）。消費した文字列テンプは探索後に seek → target の順で解放
  （FREFAC / FRETMP。変数ディスクリプタなら無操作になる）。

### 5. ELSE
- 意味論：`IF 式 THEN 文… ELSE 文…`。偽なら同一行の ELSE 以降を実行、
  真なら THEN 側を実行後に ELSE 節を読み飛ばす。ELSE は**最も近い未対応の
  IF** に対応（走査で IF トークンを数える）。THEN/ELSE とも行番号指定可。
  **`:` は ELSE の前に不要**（MS Extended の文法どおり）。
- 実装は3点セット：
  1. **偽パス（ELSESCAN）**：THEN の直後から生バイト走査。引用符内はスキップ、
     REM トークンで不発（REMH で仕上げ）、DATA トークンは DATAN 自身で
     読み飛ばす（':' か NUL まで、引用符尊重）ので、DATA や文字列の中の
     "ELSE" を誤認しない。発見時は行番号なら GOTOH、文なら IF_STMT と
     同じ作法で FETCH へ。
  2. **真パス（文としての ELSE）**：FETCH が ELSE トークンを REMH に
     ディスパッチ（行末まで読み飛ばし）。
  3. **文境界の受け入れ**：EXEC の EXCOL と PRINT のアイテムループ終端
     （PRANEXT / PRSEMI / PRZNXT）が ELSE トークンを文の終端として認める。
     これが無いと `THEN PRINT "T" ELSE …` が PRINT 内部で ?SN になる
     （MS の「コロンなし ELSE」を成立させる要）。
- EXCOL から FETCH へ渡すときは A6 を1バイト戻す（FETCH の契約は
  「文の1バイト手前」。戻さないと CHRGET が ELSE トークンを踏み越える）。

## 実装中に見つけて直した問題（記録）

- **奇数アドレスに落ちたコード**：RESLST 追加が 25 バイト（奇数）で、
  INIT が $1AD（奇数）にずれ、emu_strict が起動直後にアドレスエラーで
  死んだ（通常 emu は寛容で全テスト合格してしまうところだった）。
  終端 $00 の後にパッドバイトを1つ入れて偶数 parity を回復。
  なお emu_audit はデータアクセスしか記録しないため、この種の
  「奇数 PC フェッチ」は検出できない。strict が正解の番人。
- **FE_UF / FE_UFN の取り違え**：CHKNUM を持つのは FE_UFN の方。
  USR("A") が ?FC になっていたのを FE_UFN 経由に直して ?TM に。
- **asm68k-py の変位0 BRA 誤符号化**（SGNFN のコメントにある既知の罠）：
  IF_FALSE の `BRA ELSESCAN` が次命令への分岐になり誤符号化。
  fall-through に変更。分岐チェッカが ext-sim で検出、ext-hw では
  見逃していた（境界に偶然一致）ので、目視でも確認した。
- テスト側のミス2件（実装でなくテストデータ）：USR 定数ルーチンの
  オペコード $103C（MOVE.B #imm,D0）→ $10BC（MOVE.B #imm,(A0)）が正解。
  ベクタ番地の10進換算 836→820（$334）。

## テスト結果（run_ext1.py、132/132 ×2ラン）

- ビルド4フレーバー＋忠実バイナリの size/sum ゲート。
- 分岐チェッカ：両 ext リスティングで 0 bad / 0 bad。
- 仕様セッション（ext-sim、バイト完全一致リージョン **102件**）：
  &H（桁境界・大値・&HDEF の CRUNCH 罠・エラー）、USR（未設定 FC、
  恒等・定数の往復、?TM）、DEEK/DOKE/LEEK/LOKE（奇数アドレス、
  ビッグエンディアン、符号なし、範囲エラー）、INSTR（開始位置・
  不一致・空文字列・テンプ混在・エラー流儀）、ELSE（真偽・行番号形・
  入れ子内外・DATA/文字列/REM の誤認なし・PRINT の ';' ',' 直後・
  ダイレクトモード）、CTRL-C ブレーク（run_break セッションA相当）。
- ASCIIART：ext-sim / ext-hw / ext-hw-strict で golden バイト一致。
- ext-hw 合成ブート（通常／strict 両方）：バナー、40960 BYTES FREE、スモーク。
- 回帰：run_break.py（m5d ゲート＋run_hw を内包）合格。
  拡張フレーバーでの run_m5d カスケードも 116/118（既知 ulp 2件のみ）。

## ext-hw のレイアウト判断（ZPBASE 移動）

EXT hw のコードは忠実版の 16KB 予算を 131 バイト超過した。コードを
詰めるより、EXT hw 専用 config（`10-config-hw-x.asm`）で **ZPBASE を
$34000 → $34400 に移した**（唯一のレイアウト差分）。FNTAB $34800、
TXTTAB $35000、MEMSIZ $3F000、スタック $40000、**BYTES FREE 40960 は不変**。
論理ページ（PEEK/POKE/USR ベクタ）は ZPBASE 相対の設計なので、
ユーザから見える意味論は変わらない。コード側の余裕は 866 バイト
（第2バッチの HEX$ / RENUM 分を見込む）。

## ファーム配列とローダの再生成

- `firmware/msbasic68k.c/.h`：EXT sim イメージから再生成・検証済み
  （`gen_msbasic68k.py --bin ../phase1/msbasic68k-ext.bin
  --expect-size 16526 --expect-sum 33635`、抽出バイト一致を確認）。
  gen スクリプトには `--expect-size/--expect-sum` を追加（既定値は
  忠実版のまま）。`dualboot-integration.md` 末尾に追記済み。
- ローダ：`msbasic68k-hw-ext-loader.bas` が build.py ext-hw の正規の
  生成物。タスク指定の `msbasic68k-hw-loader.bas` にも同じ EXT 版の
  内容を置いた（ローダ自身のヘッダと LOAD OK 行にサイズ／sum が
  明記されるので判別可能）。**注意**：`build.py hw`（run_hw.py 経由を
  含む）を実行すると `msbasic68k-hw-loader.bas` は忠実版イメージから
  再生成されて戻る。EXT 版で固定したい場合は build.py ext-hw の後に
  再コピーすること。EXT hw の LOAD OK 表示は
  `LOAD OK - 16534 BYTES AT $30000, SUM 12581`。
