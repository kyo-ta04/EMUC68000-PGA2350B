# M5c 結果メモ — 配列・整数変数・DEF FN

2026-11-19。イメージ 12,345 バイト（M5b の 11,109 から +1,236）。検証は
`run_m5c.py`：**111/111 checks PASS**（M5c 本体 105 件＋分岐チェッカ 2 件＋
回帰 run_m1.py〜run_m5b.py の 6 件。回帰はすべて exit 0）。golden は
従来通り py65 上の CBM BASIC 2（mist64 orig）を正とし、期待値はすべて
golden 実測で採取した。数値末尾バイト $1D→$20 の正規化は 46 バイト。

## 実装範囲

### 1. 配列（PTRGET の配列経路、DIM、ARYTAB 配置）

- 変数領域のレイアウトは原典通り：スカラー領域 [VARTAB, ARYTAB) の後ろに
  配列ブロックを [ARYTAB, STREND) に連結配置する。各ブロックは
  名前（2 バイト）＋全体サイズ（ワード）＋次元数（バイト）＋次元サイズ群
  （ワード、宣言順、サイズ＝最大添字＋1）＋要素本体。要
...[truncated 6220 chars]素サイズは FP 5 バイト／文字列 5 バイト（ディスクリプタ）／整数 2 バイト。
  要素の並びは原典通り「最後の添字が最速で変化」。
- PTRGET を再構成した。入口は 3 つ：通常（DIMFLG クリア）、DIM 用
  （DIMFLG セット）、FN 名用（第 1 バイトに FN ビット $80 を立てる）。
  第 2 文字の後の分岐で、'(' が来れば配列経路へ（SUBFLG 中は原典通り
  ?SN ERROR）、FN 名解析中ならそのまま戻る（DEF FN の引数名は
  スカラーでなければならない、という原典の規則をこの形で実現）。
  また FOR が立てる SUBFLG 中の '%' を ?SN ERROR にする原典の
  規則（PTRGET の INTERR）を移植したため、`FOR I%` は golden と
  同じく構文エラーになる。
- 添字式の評価は再帰に耐える必要がある（添字の中に別の配列参照や
  FN 呼び出しが入る）。評価のたびに ARYDPT・部分結果バッファの
  基底・変数名・型フラグ群を CPU スタックのフレームに退避する
  設計にした。部分結果は ZP の SUBBUF（添字ワード列）に貯め、
  ネスト 8 段まで別領域を使う。
- 未宣言の配列参照はその場で暗黙 DIM する（各次元 11 要素）。
  DIM 済み配列の再 DIM は ?DD ERROR、次元数不一致・範囲外は
  ?BS ERROR、負添字と 32768 以上の添字は AYINT 経由で
  ?IQ ERROR、文字列添字は ?TM ERROR。すべて golden 照合済み。
- DIM 文はコンマで複数の配列（と、原典通り裸のスカラー名）を
  並べられる。生成前に REASON 式の空き確認をし、不足時は
  GARBAG を 1 回試してから ?OM ERROR。
- GARBAG に第 3 の走査（配列要素）を追加した。ブロック終端を
  GCEND で追いながら、文字列配列の要素ディスクリプタを
  スカラーと同じ GC_CHK に通す。

### 2. 整数変数

- スカラー A% は M3 以来の実装（LET_INT／GIVAYF）が既にあったが、
  代入変換が原典と食い違っていた。原典の代入は
  ROUND（拡張バイトでの四捨五入）→ AYINT → QINT の連鎖で、
  実効的には **floor（床関数）** になることを golden 実測で確定し
  （3.7→3、-3.7→-4、3.5→3、2.5→2、-2.5→-3、32767.6→32767）、
  LET_INT に ROUND_FAC を組み込んで一致させた。丸めが効く境界
  （0.29*100→29、1.15*100→115）も照合 PASS。
- **-32768 の原典バグを再現した**（下記「踏んだ問題」参照）。
  結果として A%=-32768 は golden と同じく ?IQ ERROR、
  A%=-32767.5 は -32768 が格納され PRINT できる、も一致。
- 整数配列は配列基盤と共通（要素 2 バイト、変換は要素代入でも
  同じ floor 規則：I%(1)=7.6→7、I%(2)=-7.6→-8 を照合）。

### 3. DEF FN / FN

- DEF FN は原典通り数値専用（原典冒頭コメント "NO STRINGS CAN
  BE INVOLVED"）。文字列の関数名・文字列の引数変数は定義時に
  ?TM ERROR、直接モードの DEF は ?ID ERROR、配列を引数名に
  書くと ?SN ERROR。
- 呼び出しは原典の意味論そのまま：引数式を評価 → 引数変数の
  現在値をスタックに退避 → 引数値を書き込む → 本文ポインタへ
  ジャンプして FRMNUM で評価 → 引数変数を復元する。引数変数の
  退避があるため、同名引数の FN を本文から呼んでも正しく戻る
  （FN F(X)=FN G(1)+X、FN G(X)=X*10 で FN F(3)=13 を照合）。
  引数式の中の FN 呼び出し（FN F(FN F(1))=5）も照合 PASS。
- 未定義 FN は ?UF ERROR（新設したエラーコード UF/$5546）。
  DEF 行が実行される前の呼び出しも ?UF ERROR（golden 一致）。
  再定義は後の定義が勝つ（golden 一致）。CLR/NEW で定義は
  消える（golden 一致）。
- 本文中の大域変数は通常通り見える（FN F(X)=X+Y で Y を読む）。
  ':' で続く文は DEF 行でも実行される（DATAN で本文を読み
  飛ばした後、通常の文実行に戻るため）。

## 原典から外れた点

1. **FN 定義の保存先**：原典は定義ポインタと引数 VARPNT を
   「FN ビット付き名前の疑似変数」の値領域（5 バイト）に詰めるが、
   本移植はポインタが 4 バイトで収まらないため、専用の側表
   （FNTABV=$018000、1 件 12 バイト＝名前 2＋本文ポインタ 4＋
   引数 VARPNT 4＋詰め物 2、上限 64 件、超過は ?OM）に分離した。
   利用者から見える挙動（NEW/CLR で消える、再定義で置き換わる、
   未定義は ?UF）は原典通り。実用上の差は定義保持数が 64 件
   までという点だけである。
2. **本文ポインタの約束**：原典は '=' の位置を保存する
   （TXTPTR＝最後に読んだ文字、という原典の約束のため）。
   本移植の FRMEVL は「第 1 文字に A6 が乗った状態」で入る
   約束（FRMEVL 自身が 1 バイト戻る）なので、保存するのは
   本文の第 1 文字の位置。内部表現の差のみで挙動は同一。
3. **文字列ディスクリプタの奇数アドレス問題は未解決のまま**
   （M5a からの引き継ぎ）：配列要素のディスクリプタも同じ
   配置規則なので、実機フェーズではディスクリプタ形式の
   見直しが要る。sim は奇数アドレスのロングアクセスを
   許すため検証には影響しない。
4. エラー文は従来通り 2 文字コード（?DD、?BS、?UF を新設）。
   照合は R 方式。

## 踏んだ問題

1. **-32768 は「原典のバグ」が正しかった**：当初、移植側の
   A%=-32768 が通るのは正しい改良に見えたが、golden は
   ?ILLEGAL QUANTITY を返す。原典ソースで確認すると、
   AYINT の寛容判定に使う NEG32768 定数が 5 バイト必要な
   ところ **4 バイトしか格納されていない**（ROM $D089 から
   `90 80 00 00` の後に別データの $20 が続く）ため、FCOMP の
   一致が決して起きず、指数 $90 は常時エラーになる。
   CONFIG_2C が末尾に $00 を足して直した後の版のバグであり、
   golden（CBM BASIC 2）には無い。移植は原典の AYINT の形を
   そのまま再現した（指数 >= $90 は無条件 ?IQ）。なお
   A%=-32767.5→-32768 の格納や PRINT INT(-32768) は QINT
   だけの経路なので golden でも正常、という非対称性まで一致。
2. **FN 呼び出しの ?SN ERROR（本文ポインタの 1 バイトずれ）**：
   実装直後、定義済み FN の呼び出しだけが ?SN ERROR になった
   （未定義 ?UF は正常）。sim のデバッガで SNERR にブレークを
   かけ、A6 が '=' の位置で止まること、FN レコード自体は
   正しいことを確認。上記「外れた点 2」の約束違いが原因で、
   DEF 時に SYNCHR 後の A6（本文第 1 文字）をそのまま保存
   するよう直して解決。切り分けの教訓：レコードの実バイトを
   ダンプして「保存側は正しい」と確定できたのが早かった。
3. **テスト側の誤り：同一行 READ/DATA**：`10 READ M(1),M(2):
   ... : DATA 3,4` は golden でも ?OUT OF DATA になる。
   冷えた DATPTR からの DATA 探索は行頭の文しか見ない、と
   いう原典の性質（V1/V3/V4 の切り分けプローブで確認。
   DATA を次の行に置く V5 は正常）。移植も同じ挙動だったので、
   テストを「次行 DATA で読める（G）」＋「同一行は両機とも
   ?OD（R）」の 2 件に直した。実装のバグではない。
4. 切り分けプローブの汚染：添字範囲の golden プローブで、
   同一セッション内の再 DIM（?DD）が後続プローブを軒並み
   壊した。独立プローブは名前を変えるか NEW を挟むこと
   （M5b でも踏んだ型だが、配列は状態が残りやすい）。

## M5d への引き継ぎ

- 残りの関数群：LOG/EXP/SQR/FPWRT（^ 演算子）、三角関数、
  RND、文字列関数 LEN/STR$/VAL/ASC/LEFT$/RIGHT$/MID$、
  PEEK/POKE。これで原典の関数表が埋まる。
- GET の複数変数形、ファイル I/O（GET#/INPUT#/PRINT#）は
  未実装のまま（実機フェーズの ACIA 方針と合わせて判断）。
- LIST の行番号前スペース（golden との既知の差）は最終
  段階の修正候補のまま。
- 実機フェーズの宿題（継続）：文字列ディスクリプタの
  奇数アドレス配置（配列要素も同規則）。FN 側表 FNTABV は
  sim 専用アドレス（$018000）にあるため、実機メモリマップ
  決定時に ZP か RAM 内へ移す必要がある（ZP は $310 まで
  使用済み。側表は 768 バイトあるので RAM 側が現実的）。
- 自己再帰 FN は golden でも ?OUT OF MEMORY に発散する
  （単一式では基底ケースを作れない）ため、M5c では検証対象
  外とした。入れ子呼び出しでスタック機構自体は証明済み。
