# M5g 結果メモ — CTRL-C ブレークの配線（ISCNTC 欠落の修正）

2026-11-19。対象: `msbasic68k.asm`（15,492 バイト）、検証: `run_break.py`。
判定: **完了**（新規テスト 16/16、通常 emu と emu_strict の両方で PASS。回帰は下記の通り全て従来通り）。

## 問題

Phase 1.5 Step 3 の実機スモークで発見された欠落。ISCNTC（ACIA の受信待ち確認）は M1 で機械層に実装されていたが、文フェッチ／実行ループから一度も呼ばれておらず、実行中のプログラムを CTRL-C で中断できなかった。原典（m6502.asm 2138–2139 行、mist64 では flow1.s の NEWSTT）は文境界ごとに `JSR ISCNTC` で STOP キーを確認し、検出時は STOPC 経由で STOP 文と同じ処理（文脈保存＋BREAK 表示）に入る。

## 配線箇所

原典の確認位置は NEWSTT の先頭（終端処理と OLDTXT 保存より前）。ポートでは NEWSTT が FETCH（OLDTXT 保存＋ディスパッチ）と EXEC（終端処理）に分かれているため、両方の先頭に `BSR BRKCHK` を置いた。

- **EXEC 先頭**が原典の正確な対応位置。文が返ってきた直後で、A6 は直前の文の終端（':' または NUL）、CURLIN はその文の行を指している。行をまたぐブレークでも原典と同じ行番号が "BREAK IN n" に出て、保存は終端位置＋CONTMD=0 になる。
- **FETCH 先頭**は EXEC を経由せずに文へ到達する経路（GOTO、RUN、CONT の CONTMD=1 再開、IF...THEN 文）をカバーする。実機では GOTO ループの最中に届いた $03 を受けるのはこちら。

## BRKCHK / BRKGO の意味論

シリアル ACIA には STOP 専用チャンネルが無いので、チェックは**入力ストリームの先頭だけ**を見る（BRKCHK、機械層に配置）。

1. pushback が占有されている → そのバイトが先頭であり、BRKCHK 自身が入れた以上 $03 でないことが確定 → 何もしない。
2. ACIA に受信待ちが無い → 何もしない。
3. 受信待ちがある → 1 バイト読む。$03（CTRL-C）なら BRKGO へ（戻らない）。それ以外は pushback に退避し、次の入力消費者が順序通り受け取る。**チェックが type-ahead を食うことはない。**

BRKGO は原典 STOPC／ポートの STP_DO と同じ保存・表示を行う。

- プログラム実行中: OLDTXT := A6、OLDLIN/OLDCIP を保存。CONTMD は A6 の位置で決める。終端（':'/NUL）なら 0（CONT は EXEC から再開）、現在行の text-1（CURLINP+5、FETCH 経由の到達）なら 1（CONT は FETCH から再開）。FETCH 自身の境界保存と同じ判別。
- 直接モード: 保存なし、"BREAK" のみ表示（原典の DIRIS 経路、STOPH と同じ）。
- 表示形式は STOP 文と同一（"BREAK IN  20" 形式。run_m5b.py で golden 照合済みのもの）。

## pushback の設計

- ZP に `PUSHBK`（ZPBASE+$330、1 ワード: +0 有効フラグ、+1 文字）を新設。ZPSIZE を $0330 → $0332 に拡張（build_hw.py の定数も追随）。
- 消費者側は機械層に閉じ込めた。
  - `MONRDKEY`（ブロッキング）: pushback を ACIA より先に返す。INLIN が共用のため、READY の行入力と INPUT の両方が自動的に対象になる。
  - `MONPOLKEY`（新設、ノンブロッキング）: GET が直接 ACIA を読んでいた箇所を置換。可否は文字ではなく D1 のスクラッチで報告するので、待っているのが NUL バイトでも「あり」と正しく返る。
  - `ISCNTC`: pushback のバイトも pending として数えるよう更新。
- ACIA データレジスタの読み手はこの 3 経路のみ（ソース全体を grep で確認済み）。解釈側（CHRGET 等）は一切変更していない。

## INPUT 待ち中の $03 の扱い（判断）

**採用: データとして扱い、ブレークしない。** INPUT は 1 文の実行中であり、文境界という粒度がこの設計の割り切り。理由:

1. CBM 原典で INPUT 中に止まるのは、KERNAL CHRIN の内側で IRQ 駆動の STOP フラグを見るからで、シリアル ACIA には相当する別チャンネルが存在しない。バイトストリーム上で $03 はデータと区別できない。
2. 機械層（INLIN/MONRDKEY）で $03 を横取りすると、文字列 INPUT のデータとしての $03 や、数値 INPUT の REDO 再入力の意味論まで巻き込む。
3. 本件の核である「計算中のブレーク」は文境界チェックで完全にカバーされる。INPUT の行を確定（CR）した後に残った $03 は、次の文境界で通常通りブレークする。

将来 CBM 式に寄せたい場合は、INLIN に「CURLIN ≠ $FFFF のときだけ $03 をブレーク扱いにする」ゲートを付けるのが拡張点になる（INLIN の呼び手は READY の MAIN と INPUT の QINLIN のみのため）。

## テスト（run_break.py、新規）

golden ハーネスの ISCNTC フックは常時「押されていない」を返すため、ブレーク自体は golden 照合できない。68K 単独で、STOP 文で照合済みの表示形式とバイト単位で照合した。

- **A**: GOTO ループ（10 GET A$ / 20 GOTO 10）に "Z"＋$03 を投入。'Z' は直接行の境界で pushback され、最初の GET が受け取り、$03 がループを止める → `BREAK IN  10`。
- **B**: 犠牲バイト 'Z'＋$03 を投入した RUN。GET が pushback の 'Z' を受け、$03 が 10 行の終端でブレーク。CONT で再開して FOR 1..100 を完走し `I= 101` を表示。A$ に "Z" が残っていることも確認。
- **C**: FOR ループ＋INPUT のプログラムに "HELLO\r" を先行投入。先頭バイトは境界チェックで pushback されるが、INPUT は行全体を正しく受け取る（`GOT:HELLO`）。
- **D**: 直接文の後ろに $03 を置くと、その文自体の境界で受けられ、裸の `BREAK`（保存なし・IN サフィックスなし）になる。原典の直接モードの挙動通りで、これを固定した。
- FIFO ハーネスの限界: 「RUN と書かれた後に $03 を置く」と RUN という直接文の境界で先に受けられる（上記 D の通り、原典でも同じ）。GOTO サイクルの途中での到着タイミング自体は FIFO では再現できず、実機側の受け口は FETCH 先頭のチェックが担う。

結果: **16/16 PASS（通常 emu）**、**16/16 PASS（emu_strict、MSB_EMU 差し替え）**。分岐チェッカ 2 種とも 0 bad。
